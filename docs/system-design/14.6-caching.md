# 14.6 System Design: Caching Layers & Cache Stampede Defense

---

## 1. What It Is in Plain Words
Caching stores frequently accessed, computationally expensive data in high-speed, volatile storage (such as RAM or CDN edge servers) so subsequent requests can be served in sub-milliseconds without hitting the primary database.

---

## 2. Whether and How THIS Project Uses It
* **Current Implementation:**
  1. **Browser Video Byte-Range Cache:** HTML5 `<video>` tags store streamed MP4 chunks in the browser's disk cache.
  2. **Edge CDN Caching:** ImageKit caches video assets globally with public edge headers.
* **Not Yet Implemented:** Application-tier caching (Redis) is currently **not implemented**. The backend queries MongoDB on every hit to `GET /api/food`.

---

## 3. End-to-End Multi-Tier Caching Architecture


## 4. Caching Strategies Compared

| Strategy | Read Path | Write Path | Consistency | Latency | Fit With Reel Feed |
|---|---|---|---|---|---|
| **Cache-Aside (Recommended)** | Checks cache; on miss, reads DB & populates cache | Writes directly to DB; invalidates or updates cache | Eventual (TTL based) | Low | **10/10 (Optimal for read-heavy feeds)** |
| **Write-Through** | Reads from cache | Writes to cache AND DB synchronously | High | High write latency | 6/10 (Slows down like toggles) |
| **Write-Back (Write-Behind)** | Reads from cache | Writes to cache; asynchronously flushes to DB | Low (Risk of data loss on crash) | Ultra-low write latency | 8/10 (Great for ultra-high QPS like tickers) |
| **Write-Around** | Reads from cache | Bypasses cache; writes directly to DB | Moderate | High read latency on first hit | 7/10 |

---

## 5. Cache Eviction Policies Compared
* **LRU (Least Recently Used) (Chosen):** Discards keys that have not been read for the longest time. Ideal for viral video feeds where old dishes naturally lose viewership.
* **LFU (Least Frequently Used):** Discards keys with the lowest access count. Vulnerable to retaining historic viral videos that are no longer trending.
* **FIFO (First In, First Out):** Evicts oldest inserted keys regardless of access frequency. Inefficient for video feeds.

---

## 6. Cache Invalidation & The Cache Stampede Problem
* **The Stampede (Thundering Herd):** When a hot cache key (e.g. `feed:trending`) expires, 5,000 concurrent requests miss the cache at the exact same millisecond and flood MongoDB simultaneously, crashing the database.
* **Remediation Strategy: Mutex Distributed Locking with Redis:**
  ```javascript
  async function getTrendingFeed() {
      let feed = await redis.get("feed:trending");
      if (feed) return JSON.parse(feed);

      // Attempt to acquire distributed lock (SET NX EX)
      const lockAcquired = await redis.set("lock:feed:trending", "1", "NX", "EX", 5);
      if (lockAcquired) {
          // Exactly one worker queries database and repopulates cache
          feed = await foodModel.find({}).sort({ likeCount: -1 }).limit(20);
          await redis.setex("feed:trending", 60, JSON.stringify(feed));
          await redis.del("lock:feed:trending");
          return feed;
      } else {
          // Other workers wait 100ms and retry reading from cache
          await sleep(100);
          return getTrendingFeed();
      }
  }
  ```

## 7. Redis vs Memcached vs In-Memory Maps

| Solution | Data Structures | Persistence | Cluster Replication | Multi-Threading | Fit With This Project |
|---|---|---|---|---|
| **Redis (Chosen)** | Hashes, Lists, Sets, ZSets, Strings | RDB Snapshots + AOF | **Master-Replica + Sentinel** | Single-threaded (I/O threaded in v6+) | **10/10** |
| **Memcached** | Simple Strings only | None (Pure Volatile) | Client-side sharding only | Multi-threaded | 6/10 (Lacks data structures for sorted feeds) |
| **Node.js Memory Map** | JavaScript Objects | None | None (Per-process memory) | Single-threaded | 3/10 (Leaks RAM, not shared across cluster) |

---

## 8. What Breaks at 10x, 100x, 1000x Load
* **10x:** MongoDB CPU hits 60% due to full collection scans on `/api/food`; fixed by adding a 60-second Redis cache.
* **100x:** Single Redis instance saturates bandwidth; fixed by deploying Redis Cluster with read replicas.
* **1000x:** Redis memory exhaustion; fixed by enforcing strict LRU memory caps (`maxmemory-policy allkeys-lru`) and storing only serialized food IDs rather than full objects.

---

## 9. 30-Second Spoken Answer
> "We employ a multi-tier caching hierarchy: browser byte-range caching for active video chunks, ImageKit edge caching for global media delivery, and an application Cache-Aside pattern in Redis for our public feed. 
> 
> To defend against cache stampedes on viral reels, we use Redis distributed locks with `SET NX EX` so only a single thread recomputes the feed while other requests wait, preventing database connection collapse."
