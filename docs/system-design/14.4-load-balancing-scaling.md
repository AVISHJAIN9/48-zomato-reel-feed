# 14.4 System Design: Load Balancing & Horizontal Scaling

---

## 1. What It Is in Plain Words
Load balancing distributes incoming client network traffic across a pool of backend servers to prevent any single machine from becoming a bottleneck, ensuring high availability, fault tolerance, and zero-downtime deployments.

---

## 2. Whether and How THIS Project Uses It
* **Current Status:** In local development, the app runs as a single Express process on port 3000 without an external load balancer.
* **Production Architecture:** 
  * Because the Express server is completely **stateless** (user authentication is maintained via signed JWT cookies, not server memory), instances can be duplicated behind an **Application Load Balancer (ALB)** with zero requirement for sticky sessions.

## 3. Load Balancing Algorithms Comparison

| Algorithm | Routing Heuristic | Best Use Case | Risk / Drawback | Fit With This Project |
|---|---|---|---|---|
| **Round Robin** | Cycles sequentially (1, 2, 3...) | Identical server specs, uniform requests | May overload a server handling a slow video upload | 8/10 |
| **Least Connections (Chosen)** | Routes to server with fewest active sockets | Varying request runtimes (uploads vs quick feed reads)| Slightly higher balancer CPU overhead | **10/10 (Optimal for mixed upload/read traffic)** |
| **IP Hash** | Hashed client IP points to fixed node | Sticky session requirements | Causes hot nodes behind large corporate NAT IPs | 4/10 (Unneeded since app is stateless) |
| **Weighted Response Time**| Routes to fastest responding server | Heterogeneous server hardware | Complex metrics collection | 7/10 |

### Layer 4 (Transport) vs Layer 7 (Application) Load Balancing
* **Layer 4 (NLB):** Operates at TCP level. Ultra-fast (millions of packets/sec), but cannot inspect HTTP headers, paths, or cookies.
* **Layer 7 (ALB) (Chosen):** Operates at HTTP/HTTPS level. Can inspect paths (routing `/api/food` to Feed service and `/api/auth` to Auth service) and evaluate cookie headers.

## 4. Single Points of Failure (SPOF) & Remediation

| Component | Current Failure Risk | Production Solution |
|---|---|---|
| **Express API** | Single container crash drops all users | Deploy in AWS Auto Scaling Group across 2+ Availability Zones with minimum 2 instances. |
| **MongoDB Database** | Single database failure halts all reads/writes | Deploy MongoDB Atlas 3-node Replica Set (1 Primary, 2 Secondaries) with automated 30s failover. |
| **ImageKit CDN** | Third-party service outage breaks video streaming | Implement multi-CDN failover (e.g. Cloudflare / CloudFront backup origin with sync). |

## 5. Health Checks & Zero-Downtime Rolling Deploys
* **Health Check Endpoint:** In [`app.js:17-19`](file:///Users/avishjain/avishjain9-repos/55-zomato-reel-feed/zomato/backend/src/app.js#L17-L19), `GET /` returns `200 OK`. The ALB pings this endpoint every 10 seconds.
* **Rolling Deploy Lifecycle:**
  1. ALB deploys Version 2 containers alongside Version 1.
  2. ALB waits for V2 containers to return HTTP 200 on `GET /`.
  3. ALB shifts traffic to V2 and drains existing connections on V1 before terminating old containers.

---

## 6. What Breaks at 10x, 100x, 1000x Load
* **10x:** Single server hits 80% CPU; resolved by spinning up 2 worker nodes behind Nginx.
* **100x:** Node cluster saturates MongoDB connection pool limit (100 sockets per container $\times 10$ nodes = 1,000 connections); resolved by deploying PgBouncer equivalent or MongoDB Atlas serverless connection proxy.
* **1000x:** Balancer itself saturates network bandwidth; resolved by deploying AWS Network Load Balancer (L4) in front of ALBs (L7).
